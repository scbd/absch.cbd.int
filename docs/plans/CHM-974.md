# CHM-974: Register admin triage filters (notification / organization / government)

> Epic: CHM-970. Depends on CHM-973 (list view, In Progress, this branch) and
> CHM-972 (facet endpoint, now implemented and running locally at
> `localhost:8000`). Design source: [ADR-0003](../adr/0003-record-snapshot-on-workflows.md),
> [PRD](../prd/workflow-admin-triage-view.md).
>
> **Deviation from the ticket's original design, decided in a grilling session
> on 2026-08-10-11**: the PRD/ticket call for the filter control to take its
> "option source as an injected strategy" (notification from Solr, org/gov
> from the facet endpoint) so a future record type could plug in different
> sources. That generalization was explicitly deferred to a separate future
> epic — this epic stays submission-only — so this plan hardcodes the three
> filters directly instead of building the pluggable-strategy abstraction.
> Separately, the real facet endpoint (confirmed by hitting it live) already
> returns all three fields (`notifications`, `organizations`, `government`)
> uniformly, so there's no longer even a practical reason for two different
> data sources — Solr is only needed for *display-name* resolution, not for
> sourcing the filter values themselves.

## Confirmed facet endpoint contract (verified live against localhost:8000)

```
GET /api/v2013/workflows/facets?fields=notifications,organizations,government&q=<JSON>
```

- `fields`: comma-separated, plain leaf names (no `data.recordFields.` prefix).
- `q`: same JSON-stringified Mongo query shape `queryWorkflows` already sends.
- Response: object keyed by each requested field name → array of
  `{ count: number, value: string }` (empty array, not omitted, when nothing
  matches — confirmed: `{"government": []}`).

**Assumption to verify first in implementation** (undiscoverable from this
repo alone — the storage schema lives in the API repo): the Mongo field path
storing each snapshot value is `data.recordFields.notifications` /
`data.recordFields.organizations` / `data.recordFields.government` (plural,
matching the facet endpoint's own field-keying) rather than the singular
`data.recordFields.notification` ADR-0003's prose uses. Verify by calling
`GET /api/v2013/workflows/:id` against a real submission workflow and
inspecting `data.recordFields` before wiring the filter query — if it's
singular, swap the field names used when building the Mongo query object
(the facet endpoint's `fields` param stays plural either way, since that's
already confirmed).

## Intent

Add three combinable content filters (notification, organization, government)
to the CHM-973 triage list, with contextual counts (facet values scoped to
the current query) and human-readable display names instead of raw
identifiers.

## Approach

1. **`app/api/workflows.js`** — add `getWorkflowFacets({ query, fields })`:
   ```js
   async getWorkflowFacets({ query, fields }) {
     const params = stringifyUrlParams({ q: query, fields: fields.join(',') });
     return this.http.get(`api/v2013/workflows/facets`, { params }).then(res => res.data).catch(tryCastToApiError);
   }
   ```
   Same `stringifyUrlParams`/error-handling pattern as `queryWorkflows`.

2. **Filter state in `admin-triage-list.vue`** — three `ref<string[]>` arrays
   (`selectedNotifications`, `selectedOrganizations`, `selectedGovernments`),
   populated from checkbox clicks. Building the combined query: extend the
   existing `$and` array (realm, schema, state, 12-week cutoff) with one
   `{ 'data.recordFields.<field>': { $in: selected } }` clause per non-empty
   filter — selections within one filter are OR'd (`$in`), filters across
   dimensions are AND'd (another `$and` entry), matching standard
   faceted-search semantics and the PRD's "combine filters" story (#5).

3. **Contextual facets, simple (non-self-excluding) semantics** — per PRD
   story #6 ("values that exist among requests matching my *current*
   filters"), taken literally: one `getWorkflowFacets` call per filter/page
   change, passing the *same* combined query (all three dimensions' current
   selections included) and `fields: ['notifications','organizations','government']`
   in a single request. This does **not** implement the fancier e-commerce
   pattern of excluding a dimension's own filter when computing its own
   counts — nothing in the ticket asks for that, and it would need N facet
   calls instead of one. Flag as a design simplification, not an oversight,
   if it comes up in review.

4. **Display-name resolution** — facet values are raw identifiers; resolve
   after each facet fetch, only for the values currently shown in the three
   dropdowns (not eagerly for the whole realm):
   - **Government**: `getCountry(code)` from `app/api/countries.js:15`
     (already ES-module, cached, Vue-friendly) — call once per unique code.
   - **Organization**: Solr query, same pattern as `app/api/realms.js:33-43`
     / `resource-mobilisation-2020.vue:407-412` —
     `identifier_s:(<guid1> <guid2> ...) AND schema_s:ORG`, `fields:
     "identifier_s,title_s"`. GUIDs may carry an `@N` revision suffix (seen
     live: `D70027E0-...@2`) — strip it before querying, the same way
     `documentIdWithoutRevision` (`~/components/scbd-angularjs-services/services/utilities.js`,
     already imported in `record-loader.directive.js`) does for record IDs.
   - **Notification**: Solr query, exact pattern from
     `view-submission.directive.js:40-46` — `identifier_s:(<ids>) OR
     symbol_s:(<ids>)`, `fields: "identifier_s,title_s,symbol_s"`.
   - All three batch-resolve (one Solr/countries call per filter type per
     facet refresh, not one call per value).

5. **UI — hand-rolled BS5 checkboxes.** Confirmed via research: no existing
   Vue/BS5 multi-select-with-counts component in `app/components/common/` to
   reuse (`km-select` is AngularJS-only and off-limits per the migration
   ratchet — no new Vue form may wrap an ng km-control). Each filter group:
   a heading + a list of `<div class="form-check">` checkboxes showing
   `"<display name> (<count>)"`, matching the mockup's visual intent within
   BS5 (per the earlier BS5 restyle decision) rather than the mockup's raw
   custom-CSS chip/checkbox markup.

6. **Tests** (ships in this PR, mirroring `test/api/workflows.spec.ts`):
   - `getWorkflowFacets` builds the correct `fields`/`q` params and returns
     the parsed facet object (stub `this.http`, same style as the existing
     `queryWorkflows` tests).
   - Query-building: given a set of selected filter values across the three
     dimensions, the combined Mongo query has one `$in` clause per non-empty
     dimension. This is the seam the PRD calls out as highest-value
     ("filter state in → correct request params out").

## Behavior

- Three filter groups (Notification, Organization, Government) render above
  the CHM-973 table, each showing checkboxes with live counts from the facet
  endpoint, scoped to the current combined filter state.
- Checking/unchecking a value re-queries both the list (`queryWorkflows`) and
  the facets (`getWorkflowFacets`) with the updated combined query, resets to
  page 1.
- Checkbox labels show resolved display names (notification symbol/title,
  organization title, government/country name), never raw identifiers.
- No content filter selected → behaves exactly as CHM-973 today (unfiltered
  pending-submission list).
- Existing CHM-973 sort/pagination/row-click behavior is unchanged.

## Tests

- `test/api/workflows.spec.ts` (extended): `getWorkflowFacets` param-building
  and response pass-through.
- New `test/views/register/` or co-located query-builder unit test (pure
  function, extracted from the component) for the filter-combination logic:
  N selected values across M dimensions → correct `$and`/`$in` query shape.
- Manual browser verification (no component-test infra, per repo
  convention): select a notification filter, confirm the list narrows and
  organization/government counts update to reflect only that notification's
  requests; combine two filters; clear filters; confirm display names appear
  correctly for all three types.

## Risks

- **Unverified storage field name** (see Assumption above) — first thing to
  check in implementation, before writing the query-builder.
- **Solr escaping**: GUID-like organization identifiers and notification
  codes both need proper Solr special-character escaping (reuse the existing
  `escape()` helper from `~/services/solr/queries.js`, already used in
  `app/api/realms.js`) — unescaped identifiers containing `@`, `-`, or other
  Solr-special characters could break the query silently.
- **N+1 risk avoided by design**: batching all identifiers of one type into
  a single Solr `identifier_s:(...)` OR-query per facet refresh, not one
  query per value — called out explicitly in Approach step 4 so it doesn't
  regress during implementation.

## Success criteria

1. `getWorkflowFacets` and query-builder unit tests pass → verify: `yarn vitest run`.
2. `yarn typecheck` and `yarn lint` pass on the new/changed files.
3. Manual check against the real local API (`localhost:8000`): filters
   narrow the list, counts are contextual, display names resolve correctly
   for all three filter types, combining filters works, clearing filters
   returns to CHM-973's unfiltered behavior.
