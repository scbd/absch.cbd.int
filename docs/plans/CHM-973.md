# CHM-973: Register admin submission triage list view

> Epic: CHM-970. Backend sibling: CHM-971 (In Progress, PR pending). Depends on
> nothing new server-side — works against the existing workflow query
> endpoint. Follow-up slice CHM-974 (filters/facets) is out of scope here.
> Design source: [ADR-0003](../adr/0003-record-snapshot-on-workflows.md),
> [PRD](../prd/workflow-admin-triage-view.md).

## Intent

Give SCBD administrators a paginated, sortable list of pending `submission`
workflow requests in the Register admin area, so they can triage the queue
without opening each request individually. Clicking a row lands on the
existing request review flow. No filtering by record content yet (CHM-974).

## Approach

Reuse the existing workflow query contract end-to-end; the only new surface
is a Vue 3 list view and a thin API method to reach it from Vue.

1. **`app/api/workflows.js`** — add `queryWorkflows({ query, count, length,
   skip, sort, fields })`, wrapping the same `GET api/v2013/workflows`
   endpoint the AngularJS `IWorkflows.query()` already calls (params `q`
   (JSON-stringified), `l`, `s`, `sk`, `c`, `f`). Model the method on
   `ArticlesApi.queryArticles` (`app/api/articles.js:16-23`) — build params,
   `stringifyUrlParams`, `.then(res => res.data).catch(tryCastToApiError)`.
   The AngularJS service and its consumers (the existing requests
   dashboard) are untouched — this is an additive method on the Vue class.

2. **New route** — add an entry to `app/routes/common-routes.js` alongside
   the existing `/register/admin/*` block (lines ~148-156), modeled on
   `/register/requests/:workflowId` (line 121, the existing Vue-rendered
   example): `mapView(vueViewWrapper)` + `resolve: { ...commonRouteUrls.<new
   entry>, securized: securize(['Administrator']) }`. Add the matching
   `commonRouteUrls` entry with a lazy `import('~/views/register/admin-triage-list')`.

   - Proposed path: `/register/admin/triage`.
   - **Decision:** ship the route/nav entry on all three clearinghouses.
     `submission` is a CHM-only schema, so `queryWorkflows` naturally returns
     an empty list on ABSCH/BCH — no clearinghouse-gating needed.

3. **New view — `app/views/register/admin-triage-list.vue`** (flat in
   `app/views/register/`, matching where `workflow-request.vue` and
   `requests.js/html` already live). Pattern to copy: `article-search.vue`'s
   `ref` state (`pageNumber`, `recordsPerPage`, `resultCount`, `loading`) +
   the shared `app/components/common/pagination.vue` widget (`recordCount`,
   `recordsPerPage`, `currentPage` props; `@changePage` emit). On mount and
   on page/sort change, call `workflowsApi.queryWorkflows(...)` with
   `query: { schema: 'submission', state: 'running' }` (same "pending" filter
   the AngularJS `requests.js:buildQuery()` uses today) and the current
   page/sort. Row click routes to `/register/requests/:workflowId`
   (`workflow-request.vue`, the existing redirector into record review).

4. **Wire up vitest** (first test infra in this repo, per the migration
   ratchet — ships in this PR alongside the code it covers):
   - Add `vitest`, `@vue/test-utils`, `happy-dom` to devDependencies.
   - Add `vitest.config.js` (root) and a `"test": "vitest run"` script in
     `package.json`.
   - `test/api/workflows.spec.ts` (mirrors `app/api/workflows.js`): stub the
     `ApiBase` HTTP client the way the PRD's testing section calls for —
     filter/paging state in, correct request params (`q/l/s/sk/c`) out.
     `queryArticles` is the closest prior art for what "thin API class
     designed to be stubbed" looks like here.

## Behavior

- Route `GET /register/admin/triage` (working title) renders only for users
  with the `Administrator` role (`securize(['Administrator'])`); anyone else
  is redirected exactly as the existing admin routes redirect today.
- List shows pending (`state: 'running'` AND `createdOn` within the last 12
  weeks) `submission` workflows, paginated and sortable, matching the
  AngularJS `requests.js:buildQuery()`'s "Pending" bucket exactly (so behavior
  is a strict UI subset of what staff already see there, minus the content
  filters CHM-974 adds later).
- Clicking a row navigates to `/register/requests/:workflowId`, which already
  resolves the underlying record and forwards to the record view.
- The existing AngularJS requests view, dashboard, and `IWorkflows` service
  are not modified — this ships as a pure addition.

## Tests

- `test/api/workflows.spec.ts`: `queryWorkflows` builds the correct `q/l/s/sk/c`
  params from filter/paging/sort input (stub `this.http`, assert on the call
  args) — the seam the PRD calls out as highest-value and cheapest to test.
- Manual browser verification (no component-test infra exists yet, per repo
  convention): triage list renders for an Administrator on CHM, paginates,
  sorts, and a row click lands on the existing request review flow. Confirm
  ABSCH/BCH deployments still boot and their existing Register admin routes
  are unaffected.

## Risks

- **Sort param wire format is UNVERIFIED against the real server — needs
  manual QA before merge.** The legacy AngularJS `IWorkflows.query()` sends
  `sort` as a raw object (Angular's param serializer flattens it to
  `s[field]=-1`), but it's also never actually exercised — `requests.js`
  computes a local `sort` variable and then passes `null` instead of it, so
  the legacy view has never sorted via the server. The new `queryWorkflows`
  instead JSON-stringifies `sort` into a single `s` string, matching how `q`
  and `f` are already sent. This is a *guess* at the correct format, not a
  proven one, since the actual parsing logic lives in the separate API repo
  and isn't inspectable from here. **Do not treat the passing unit test as
  proof this works** — it only asserts the shape my own code produces, not
  that the server accepts it. Verify in the browser that clicking a sortable
  column header actually reorders the list before merging.
- **First vitest setup in the repo** carries general new-tooling risk (config
  drift with the Rollup/Babel build); scoped narrowly to one config file and
  one spec file to keep the blast radius small.

## Success criteria

1. `queryWorkflows` unit test passes → verify: `yarn vitest run`.
2. `yarn typecheck` and `yarn lint` pass on the new files.
3. Manual check: sign in as a CHM Administrator, visit the new route, see
   paginated/sorted pending submission requests, click through to review.
4. Manual check: ABSCH and BCH dev builds still start and their admin routes
   are unchanged.
