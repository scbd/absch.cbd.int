# CHM-1006: Bulk import: offer to submit imported drafts for review

> Type: New Feature · Component: ABSCH · Jira status when planned: Selected for Development
> Branch: `blaise/feat/CHM-1006-bulk-import-submit-for-review` (stacked on
> `blaise/feat/CHM-1007-bs5-bulk-import-dialogs`, PR #1563 — the done dialog markup it builds on).
> Design settled in the grilling session (2026-11-09); see the Jira description. Decisions are final.

## Intent

After a bulk import creates drafts, the done dialog offers **Submit for review** or **Later**.
Submit starts the workflow for every draft created, one at a time, via the 2023 `publishDraft`
endpoint. Server validation failures are shown per row; failed rows stay as drafts.

## Findings

- `KmDraftsApi.publishDraft(schema, identifier, document, { additionalInfo, isNew })`
  (`app/api/km-document.ts:154`) already exists. Today it is only used for linked records
  (`submit-documents.ts:31`, `isNew: true`). It POSTs when `isNew`, otherwise PUTs.
- Drafts are already saved with `saveDraft` before submit (first-version rule from grilling), so the
  record exists as a draft → **PUT** (`isNew` omitted) is the expected call. **Unverified against the
  server**: confirm on the first run; if PUT rejects, switch to `isNew: true`. One-line change.
- `UploaderState` `done` already carries `progress: RowProgress[]` (`ok`/`error` per row, with
  `message`) and `documents` live only in `confirmImport` — **the built documents are dropped at
  `done`** (`use-bulk-import.ts:145`). Submit needs them, so carry `documents` into `done`.
- Row → document mapping: `documents[rowIndex]`; skip rows whose `progress[rowIndex].status !== 'ok'`.
- `tryCastToApiError` (`api-base.js:92`) throws `{cause, ...data}` only when the body has `code` or
  `statusCode`; otherwise a crafted `Error` whose `cause` is the axios error. The validation body is
  `{errors:[{code, property}]}`, so read it via `err.errors ?? err.cause?.response?.data?.errors`.
- Message source: code table + `km-document-validation.json` (`Error.Mandatory`, `MandatoryAnyOf`,
  `InvalidValue`, `InvalidProperty`, `UnspecifiedLocale`, `UnexpectedTerm`, `InvalidType`,
  `RecordExists`); field labels `editAbsPermitT.<property>` in
  `app/app-text/views/forms/edit/abs/edit-absPermit.json`. These are merged into the AngularJS
  `translationService`, not vue-i18n — the bulk-import modal uses vue-i18n with document-type
  `messages`. Reuse by **importing the two JSON files** into a mapper (no copy of the text).
- `bulk-import-modal.vue` is 443 lines (limit 450 for new files, near for edits) → new logic goes in
  new files; the modal only wires it.

## Approach

1. **State** (`framework/types.ts`): add phases `submitting` and `submitted`; `done` gains
   `documents: DocumentRequest[]`. `submitting` = `{ preview, rawRows, progress, documents, currentPush? }`;
   `submitted` = `{ preview, rawRows, progress, submitted, left }`. Row status gains
   `submitted` / `draft` handled via a new `RowProgress.submit?: 'submitted' | 'draft'` field instead of
   changing `RowImportStatus` (keeps existing `ok`/`error` meaning = draft saved).
2. **`framework/submit-for-review.ts`** (new): `submitForReview(documents, progress, { tokenReader, realm }, { onRow, onPush })`
   — sequential loop over rows with `progress.status === 'ok'`; `api.publishDraft(schema, identifier, doc)`;
   on success `onRow({ rowIndex, submit: 'submitted' })`; on error `onRow({ rowIndex, submit: 'draft', message })`
   where message = `mapValidationErrors(err)`. Returns `{ submitted, left }`. HTTP only through `KmDraftsApi`.
3. **`framework/validation-messages.ts`** (new): `mapValidationErrors(err): string` — extracts
   `errors[]`, maps each `{code, property}` to "`<label>`: `<message>`" using the km-document-validation
   JSON and `editAbsPermitT` label (fallback: property name, then raw code); non-validation errors →
   `err.message`. Joined with `; `.
4. **`use-bulk-import.ts`**: store `documents` in `done`; add `onSubmitForReview()` (done → submitting →
   submitted, mutating `state.progress` through the reactive proxy as `onImport` does); closing blocked
   while `submitting` (same guard as `importing` in `onClose`).
5. **`bulk-import-done-dialog.vue`**: new optional props `canSubmit: boolean`; footer shows
   **Submit for review** (primary, focused) + **Later** (secondary) when `canSubmit`, else the existing
   single Close. New emits `onSubmit`, `onClose` (Later = existing close). Offered when `imported > 0`
   (including partial success); not when none were created.
6. **`bulk-import-modal.vue`**: pass `:can-submit="state.imported > 0"`; on `onSubmit` dismiss dialog and
   call `onSubmitForReview`; footer shows running count (`submitting`) and final summary (`submitted`);
   `rowProgressList` also covers the new phases; `onImported` still fires when the user finally closes
   (emit on Later, or on close after `submitted`). Banner text for the new phases.
7. **`bulk-import-table.vue`**: status column shows `submitted` / `draft` when `submit` is set, plus the
   existing `bi-push-err` line for the validation message.
8. **`bulk-import-modal.json`**: flat English keys only — `submitForReview`, `later`, `submitting`,
   `submitProgress` ("Submitting record {current} / {total}"), `submitDone` ("{submitted} submitted for
   review, {left} left as drafts."), `submitBannerOk`, `submitBannerPartial`, `statusSubmitted`,
   `statusDraft`, `confirmSubmitPrompt` (done-dialog body when `canSubmit`).

## Out of scope

Retry inside the modal (user fixes in the edit form); submitting linked records (already published);
non-English translations; IRCC-specific logic (generic for all bulk-import document types, but the label
lookup falls back to the property name when a type has no label file); vitest wiring.

## Verification (manual — no vitest in the repo)

1. All-valid import → done dialog shows Submit/Later; Later closes and emits `onImported`.
2. Submit → progress "Submitting record n / N", close disabled; rows turn `submitted`; summary in footer.
3. Import containing a draft the server rejects (e.g. blank `dateOfIssuance` via a hand-edited doc) →
   row `draft` with readable message ("Date of issuance: …is mandatory"); others submitted.
4. Partial import success (one row fails to save) → dialog still offers Submit; failed row skipped.
5. Zero created → no Submit button.
6. Confirm PUT vs POST in the network tab on first run; adjust `isNew` if needed.
7. `yarn lint` and `yarn typecheck` pass.

## Risks

- **PUT vs POST** for publishing an existing draft (see Findings) — resolved on first run.
- Error body shape may not reach the catch intact through `tryCastToApiError`; mapper reads three
  locations and falls back to `err.message`. Verify with a real 4xx.
- Translation JSON from the AngularJS layer imported into a Vue module: confirm Rollup resolves the
  `~/app-text/...` import in both places (the modal already imports app-text JSON, so expected fine).
- Large state-machine change (two phases + type changes) in an already large modal — kept to wiring.

## Acceptance criteria

- Done dialog offers Submit for review / Later when ≥1 draft was created; neither shown when none.
- Submit runs sequentially with progress, close blocked, per-row result in table, footer summary.
- Server validation errors appear as readable per-row messages; failed rows remain drafts.
- No HTTP outside `app/api/`; no new `$injector` or AngularJS code; lint and typecheck clean.
