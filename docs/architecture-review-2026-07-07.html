2 · Collapse the Record write path into a Record store

Strong ports & adapters

scbd-angularjs-services/services/storage.js (632) · views/forms/edit/editFormUtility.js (234) · services/workflows.js (88) · generic-service.js (84)

Before — a call crosses four thin bands

After — one thick band

Record store

inside: URL mapping · security-then-write invariant (once) · draft→document fallback · workflow create/cancel

Two adapters justify the seam: HTTP in prod, in-memory fake for form tests.

Problem: the write path stacks three shallow modules — each adds a URL string and .then(r=>r.data); the one real invariant (security check before write) is copy-pasted, not owned.

Solution: one deep Record store module (TS, in app/api/): load/draft/publish/security/workflow behind one interface; IStorage and editFormUtility become thin ng adapters over it, then die with their Views.

  • locality: publish invariant lives once
  • leverage: 32 IStorage call sites, one interface
  • edit-form tests need no ng injector
  • deletion test: IStorage vanishes, nothing reappears

Sequencing: the edit-form Views are untested and late in every realm's Phase-2 queue — invert the interface early, migrate its callers late.

7 · Folder structure — protect the contract, let the migration do the moving

Worth exploring navigability

Judged by one question: does a reader (or an AI agent) know where a thing lives, and where new code goes?

Today — homes vs junk drawers

app/api/ — HTTP, one rule, works

app/routes/ — per clearing-house, matches deploys

app/types/ · test/ — established this week

app/services/ — 30 entries: domain + utils + infra + dead code

…/scbd-angularjs-services/services/ — second “services” home

app/components/ — features + generic UI + vendored ng packages, one level

filters ×3 — services/filters.js, services/filters/, scbd-*/filters/

components/maxin/ — typo’d “mixins”, unfindable

The scatter tax — one feature, five homes

views/kb/
components/kb/
services/composables/articles.js
services/articles-service.js
app/api/articles.js
components/kb/article-api.js
the duplicate this scatter produced

No single obvious home → people create local copies. The by-kind split only works with a “one feature, one name, no feature-local HTTP” rule.

Problem: the top level matches CONTEXT.md and is worth protecting, but services/ is a junk drawer, “services” has two homes, and components/ hides which subtrees are frozen ng-era packages — so every session re-derives where things live.

Solution: no big-bang reshuffle (ng-era trees die at Phase 5; moving them buys nothing). Three cheap moves, then let each Phase-1 inversion relocate logic to its end-state home for free.

  • write the folder contract into CLAUDE.md — incl. “scbd-angularjs-* is frozen legacy”
  • “one feature, one name” rule; fix the live violation (candidate 6)
  • rename maxin/ → mixins/; pick one filters home when filter inversions start

Decide before Phase 2: kind-first (today) vs feature-first (features/kb/{views,components,api}) for Vue-era code. 127 routes get touched in Phase 2 — files can land in the right place for free, but only if the shape is chosen first.

Problem: the three clearing-house themes are hex values repeated per selector and defended with !important; the headers are three copies of the same structure; two icon fonts ship on every page.

Solution: CSS custom properties per realm ([data-realm=…] token blocks), Bootstrap 5.3 (its --bs-* vars + color modes consume the tokens), cascade layers to retire the !importants, one realm-config-driven Vue header built when the Flip needs it anyway.

  • a new theme = one token block, no override rules
  • dark mode falls out of the token model
  • 3 headers → 1 component at the CHM Flip
  • drop font-awesome 4.7; logical properties shrink RTL exceptions
  • migrated Views take scoped styles; global page CSS dissolves

Sequencing: tokens + Bootstrap 5.3 + @layer now (migration-independent) · Vue header at the CHM Flip (Phase 3 requires the shell anyway) · scoped styles per migrated View (Phase 2 opportunistic rule).

Top recommendation

1 · One Search module over the solr index

Highest leverage of the six: 33+ call sites, three copies of the same localization logic, and query building is pure — the whole implementation lands under vitest through one interface. It is also the searchService inversion the Phase-1 plan already demands, and the search Views it unblocks are the largest cluster in the Phase-2 route queue. Candidate 4 (Locale) is the runner-up: smaller, already next in the inversion queue, and the realm.ts recipe applies verbatim. One decision has a deadline rather than a priority: the kind-first vs feature-first folder shape (card 7) must be settled before Phase 2 starts moving 127 routes.
